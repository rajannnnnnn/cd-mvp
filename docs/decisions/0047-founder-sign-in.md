# 0047 — Founder sign-in: one founder, fixed by the deployment; authenticator first, a WhatsApp code only when something looks wrong

Status: accepted (2026-11-09). Supersedes the sign-in flow in ADR 0028 ("a WhatsApp code, then an authenticator code, always"). Everything else in
0028 (separate application, short sessions, no refresh, break-glass) and ADR 0043 (the console's own database login) stands.

## Context
The founder asked for: a smooth, QR-based sign-in; the founder's number put in at deployment and impossible to change by any attack; only that number
ever has access; the authenticator as the first factor and a WhatsApp code as a second layer only when a login looks suspicious (wrong codes, many
tries, industry practice); and, for this version, exactly one founder.

The old flow sent a WhatsApp code to anyone who typed an operator's number, then asked for the authenticator code. That made a WhatsApp message a
trigger anyone on the internet could pull, and it treated a phone number (which a SIM swap can take over) as the first and strongest proof.

## Options
1. **Keep it**: WhatsApp code, then authenticator, every time. Safe, but a code to WhatsApp on every login is friction, and anyone can make the
   product text the founder by typing the number.
2. **Authenticator only.** Smooth and nothing to spam, but a stolen authenticator secret or phone is then the only barrier.
3. **Authenticator first; a WhatsApp code is added when the login is suspicious** (chosen). The first proof is the one an attacker cannot trigger
   or guess; the second proof is requested only after the first has passed, so nobody can make the product message the founder by guessing.

## Decision
**One founder, fixed by configuration.** The founder's number is the setting `FOUNDER_PHONE` of the console part (required there). Access checks compare
the signed-in account's number with that setting on every request. No API, console screen or database value can add, change or replace the founder: a
row that says `platform_role = 'operator'` is not enough, and an account whose number was edited in the database stops working at once, because it no
longer equals the deployment's number. Changing the founder is a redeploy with a new `FOUNDER_PHONE` and a new enrolment, on the server.

**Enrolment is a command on the server, with a QR code.** `python -m salesai admin-enroll` (no number to type: it uses `FOUNDER_PHONE`) creates the founder
account if it does not exist, demotes any other operator account, makes a new authenticator secret, prints it as a QR code in the terminal (and the
text secret and link as a fallback), signs out every console session and forgets every trusted device. It is the only way to set up or replace the
authenticator; there is no web page for it, so whoever reaches the site cannot enrol. Running it again is the recovery for a lost phone and needs
server access. The QR is generated by the pure-Python `segno` library (no dependencies, no network).

**Sign-in.** The console asks for nothing but the 6-digit authenticator code: there is no number to type, so there is nothing to enumerate and no
WhatsApp message to trigger. A correct code then either opens a session or, when the login is suspicious, returns a five-minute ticket and requires a WhatsApp
code sent to the founder's number (the second layer). Wrong authenticator codes never cause a WhatsApp message.

A login is suspicious, and needs the WhatsApp code, when any of these is true:
- the browser is not a **trusted device**: a long random token kept in an HttpOnly, SameSite=Strict cookie, remembered server-side as a hash (at most 5
  devices, 30 days each, set only after a fully successful sign-in);
- there have been **wrong codes since the last successful sign-in** (anyone guessing is the case this exists for);
- the network is **new**: the address is outside the /24 (IPv4) or /48 (IPv6) of the last successful sign-in;
- the account was **locked** since the last successful sign-in;
- it is the first sign-in after enrolment.

Authenticator codes work once (a used step is remembered); five wrong codes (authenticator or WhatsApp) lock for fifteen minutes; sessions last 30
minutes with no refresh except a fresh authenticator code. Three wrong codes raise a High alert to the founder; a lock raises a Critical one. Every outcome is
written to the platform audit trail. The secret stays encrypted under a key only the console part can derive.

## Consequences
- The common login is one code from the authenticator app, on a device already trusted. A new device or any sign of guessing adds the WhatsApp code.
- A stolen authenticator secret alone is not enough on a new device or network; a SIM-swapped number alone is worth nothing (the WhatsApp code is only
  ever requested after the authenticator passed).
- A new dependency, `segno` (pure Python, no dependencies, widely used), for the QR code.
- One founder only. A team of operators is a different design (a list of numbers, per-person devices, per-person audit) and would be a new ADR.
- The seed's demo operator and any other `operator` rows no longer grant console access; only the number in `FOUNDER_PHONE` does.
- Requests no longer carry a phone number, so the console's sign-in screen and generated client change.

## How to revisit
If a second person needs the console: replace the single `FOUNDER_PHONE` with a deployment-time list, keep "configuration, not database" as the source of who
may sign in, and give each person their own authenticator and trusted devices. If the suspicion rules are too strict or too loose in use, they are one function
(`AdminAuth._suspicion`) and one test file (`tests/test_founder_sign_in.py`).
