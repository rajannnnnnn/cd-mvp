# 0056 The founder's identity lives in the deployment's environment: phone, email and authenticator, and a login that scales its proof to its risk

**Status:** accepted · 2026-11-25 · founder: "why is the authenticator in the database, shouldn't it be in the env?"; "add email, so the admin can log in with email, phone and authenticator, decide what to do at each login, and the deployment never changes it because the env has phone, authenticator and email fixed"; "keep a record of every founder session with all the security information: location, device and so on". Supersedes the enrolment and step-up parts of ADR 0047. ADR 0048 (sessions and security activity) stands and is extended.

## Context
ADR 0047 kept the authenticator secret in the database, encrypted under a key derived from `ADMIN_JWT_SECRET`, and made the founder's number the only identity setting. Two consequences were unwelcome: wiping or restoring the database (a fresh start, a bad restore) lost the authenticator and forced a new enrolment, and the secret's protection depended on the same environment secret that now would be needed anyway. The founder wants the three things that identify them fixed by the deployment, so that nothing in the running system can change who they are.

## Decision
1. **Three settings of the console part, all required, are the founder:** `FOUNDER_PHONE`, `FOUNDER_EMAIL` and `FOUNDER_TOTP_SECRET` (the authenticator secret, base32, at least 20 characters). The console refuses to start without them or with a malformed one. They are checked on every request (as the number was), so a session ends at once if a setting changes, and no API, screen or database value can add or change the founder.
2. **The database no longer holds the authenticator secret.** The `admin_credentials` row keeps only state (the last used code step, wrong-code counters, lock, trusted browsers, last sign-in); it is created automatically for the founder the first time it is needed, so there is no setup step for the account. A wiped or restored database therefore needs nothing re-done: the next sign-in simply behaves like a first sign-in. `python -m salesai admin-enroll` now only helps: it prints the QR for the secret in the environment (to add to a new phone), or with `--new-secret` makes a fresh secret to put into the environment (printed once, stored nowhere), and with either it signs out every session and forgets every trusted browser.
3. **What each login must prove** (decided here; the rules are one function, `AdminAuth._risk`):
   - **Routine** (a trusted browser, the usual network, no failed attempts): the authenticator code.
   - **Elevated** (a new browser, or a new network, or a lock since the last sign-in): the authenticator code and one code from the founder's WhatsApp. If WhatsApp cannot deliver (Meta down, number problem) the same step may be satisfied by a code sent to `FOUNDER_EMAIL`; the session records which was used.
   - **High** (the first sign-in on a database, wrong codes since the last good sign-in, or a new browser and a new network together): the authenticator code, **and** a WhatsApp code, **and** an email code. Two separate channels the founder controls, so no single stolen channel is enough.
   A code is only ever sent after the authenticator code passed, so nothing the platform sends (WhatsApp or email) can be triggered by guessing. Email codes are 8 digits, valid 10 minutes, single use, five tries, stored hashed, sent from `ADMIN_EMAIL_FROM` (ADR 0055). Wrong codes in any step count toward the same 15-minute lock. Extending a session or ending another still needs a fresh authenticator code.
4. **Every console session is recorded with everything the console can learn about it** (extends ADR 0048): the full address and its network, the browser and device as the browser describes them, the browser's language, the country, and the city and region when the front proxy supplies them (`ADMIN_GEO_HEADER`, `ADMIN_GEO_CITY_HEADER`, `ADMIN_GEO_REGION_HEADER`; the console itself holds no location database and says "not provided" otherwise), whether the network was the usual one, the risk the login was judged at and why, every proof used (authenticator, WhatsApp, email), when it started, when it was last used, when and why it ended (signed out, revoked, expired, ended by a new enrolment). Refused and failed attempts, locks, step-ups and revocations are in the audit trail with the same details. The console's Security screen shows all of it, and High alerts go to the founder for each Elevated or High sign-in.

## Consequences
- The secret is now in `deploy/admin/.env`: whoever can read that file can sign in with a code. It must be protected like the other secrets (file permissions, a secrets manager, never in git, never in chat). That is no weaker than before: the old key to decrypt the database copy was in the same file. A separate secrets file (a pending item) would improve it for all of them at once.
- Rotating the authenticator is: make a new secret, put it in the environment, restart the console (every session ends). Losing the phone is the same, using the saved text secret or a new one.
- A wiped database means the next sign-in is a High one (both codes). That is intended: it proves the phone and the mailbox are still the founder's.
- The first version of the console part now needs mail settings (transport, region or SMTP host, `ADMIN_EMAIL_FROM`) because it sends the email code itself, on the request path, with a short timeout. If sending fails the sign-in does not proceed and the message says so.
- Passkeys (hardware keys) remain the strongest next step and would replace the codes.

## Built
The three settings (`FOUNDER_PHONE`, `FOUNDER_EMAIL`, `FOUNDER_TOTP_SECRET`) and `ADMIN_EMAIL_FROM`, checked at startup; the secret is read from the environment and the database column is empty; the account and state row are created on first use; a session carries a fingerprint of the three settings and ends when any changes (migration 0039); the three risk levels (`AdminAuth._risk`) with the WhatsApp and email channels (`/step-up/send`, `/verify`, `/status`), a 30-second wait before a resend, an 8-digit hashed single-use email code (10 minutes, 5 tries) in `admin_email_codes`; the code email is sent directly with a 12-second limit and a failure refuses the step; session records extended with risk, proofs, city, region, language; `admin-enroll` and `admin-enroll --new-secret`; the login screen keeps its place on a refresh (the ticket is kept in the tab, progress is asked of the server, a refresh sends nothing); a Security screen in the console. Tests: `tests/test_founder_login_levels.py`, the updated `test_founder_sign_in.py`, `test_admin_auth.py`, `test_console_sessions.py`.

## Not done
City and region without a proxy that provides them; a screen to change the rules (they are code, by design); a push notification on sign-in; co-founder access (ADR 0055, still only a decision).

## How to revisit
Change what a risk level requires in `AdminAuth._risk` and `_needs`, and the tests in `tests/test_founder_sign_in.py` that name each level.
