# 0055 Co-founder console access: by email, granted and ended only by the founder, always with an expiry

**Status:** proposed · 2026-11-25 · founder: "I will grant a co-founder access and set the expiry"; "the co-founder won't have control over their access extension or revoke, I only do"; "it should be based only on email"

## Context
ADR 0047 fixed the console to exactly one founder (`FOUNDER_PHONE`, an authenticator, and a WhatsApp code only when a sign-in looks suspicious) and said a team needs a new decision. The founder wants to give co-founders temporary access with a clear end, identified by email, and wants to be the only person who can grant, extend or end it.

## Decision
1. **Grants are made on the server, never on the web.** Four commands run with the console part's environment, the same trust boundary as `admin-enroll`:
   `admin-grant <email> --until <date and time> [--role viewer|support]`, `admin-extend <email> --until ...`, `admin-revoke <email>`, `admin-grants` (list, with expiry and last sign-in).
   There is no screen, API call or database value reachable from a signed-in console session that adds, extends or ends a grant, so a stolen co-founder session (or a stolen founder session) cannot create more access. The founder's own access stays `FOUNDER_PHONE`.
2. **A co-founder is an email address and nothing else.** `admin_grants` holds the email (lower-cased), the role, the expiry, who granted it and when. No phone number and no authenticator secret are held: there is nothing to hand over or lose.
3. **A co-founder signs in with a one-time code sent to their email, and only that** (founder's choice). They type their email on the console's "Co-founder" page; if (and only if) a live grant matches the allowed list, an 8-digit code is emailed to that same address, valid 10 minutes, single use, five tries, stored hashed. The page answers the same way whether or not the address has access ("if this email has access, a code is on its way"), so nobody can find out who has access or make the platform email arbitrary people. A correct code opens a 30-minute session with no refresh (a new code is needed after that). Rate limits: 5 codes per email per hour, 20 per network per hour, five wrong codes lock that email for 15 minutes.
4. **Expiry is enforced on every request**, not only at sign-in: `authenticate` checks the grant is still there and `now < expires_at`; when time passes the session ends mid-use. **There is no permanent co-founder access, by construction:** a grant without an expiry cannot be stored (the column is `NOT NULL` with a database check that it is in the future when written and no more than `ADMIN_GRANT_MAX_DAYS` ahead), there is no "forever" option on any command, `ADMIN_GRANT_MAX_DAYS` itself is limited to 1 to 90 at startup (a larger or unlimited value stops the console starting), and `admin-extend` needs a new explicit date every time, counted from now, never "add N days". Someone who needs access for longer is granted again by the founder, on purpose, and the audit trail shows each grant. A grant that has passed is also deleted by the hourly tidy-up, with its authenticator secret. Sessions are 30 minutes like the founder's and never outlive the grant.
5. **Roles.** `viewer` (default): the boards, alerts, queues, mail and support lists, read only. `support`: also resolve alerts and answer support tickets. Neither can read a shop's chat, impersonate, delete a shop, replay or purge queues, change billing or settle an invoice, or touch grants: those stay the founder's. A role is checked at the API on every route (a `founder` dependency for the dangerous ones, a `can_write` for the support ones), and the console hides what the role cannot do.
6. **Everything a co-founder does is on the audit trail with their email.** Because email alone is a weaker proof than the founder's authenticator, every co-founder sign-in raises a High alert to the founder at once (who, which device and network, until when), and the safeguards are structural: read-only by default, never chat reading or destruction, a short session, an expiry, and the allowed-email rule. Revoking ends every session of that person at once.
7. **The login codes have their own sender, from the same SES account** (`ADMIN_EMAIL_FROM`, for example `access@yourcompany.example`, verified in SES). It is kept apart from the billing, support and account senders so that a login code is recognisable and can be filtered or alarmed on its own, and a problem with customer mail never touches sign-in. It has no `Reply-To` and no hidden copy: a reply goes nowhere. Sending a login code is the one place mail is on the request path (a code cannot wait for the scheduler): the console part sends it straight through the same transport with a short timeout; a failure says "we could not send the code, try again" and never lets the sign-in through. The console part therefore gets the mail transport settings (`EMAIL_TRANSPORT`, `SES_*`), and with `ADMIN_GRANT_ALLOWED` set but `ADMIN_EMAIL_FROM` missing it refuses to start.
8. **The deployment says which emails may ever be granted access** (`ADMIN_GRANT_ALLOWED`, a comma-separated list of rules, empty by default = nobody). A rule is one of:
   - an exact address: `priya@yourcompany.example`
   - a whole domain: `@yourcompany.example` (that exact domain only)
   - any subdomain of a domain: `@*.yourcompany.example` (`ops.yourcompany.example`, not `yourcompany.example` itself)
   - a name pattern with `*` in the name part: `ops-*@yourcompany.example`
   Matching is case-insensitive and exact on whole domain labels (`@yourcompany.example` never matches `evilyourcompany.example` or `yourcompany.example.evil.com`). A rule is refused at startup when it is too broad to mean anything (`*@*`, `@*.com`, a domain with fewer than two labels). The list is checked **three times**: when the founder runs `admin-grant` (a refusal names the rule list, not a guess), at every sign-in, and on every request. Removing a rule and restarting the console therefore ends the access of everyone it no longer covers, at once, without touching the grants. An address with a `+tag` is matched on the address as typed, so a rule for `a@x.example` never admits `a+b@x.example`.

## Consequences
- A second console identity type, and the first multi-person audit. The founder's flow does not change.
- The console part now needs the mail settings (SES or SMTP) and the sender address for these codes (`ADMIN_EMAIL_FROM`).
- **Email-only sign-in is weaker than the founder's authenticator:** whoever controls an allowed mailbox during a grant can sign in as that co-founder. That is accepted by the founder and bounded: the allowed-email rule, a mandatory short expiry, view-only or support-only rights, 30-minute sessions, rate limits, and a High alert to the founder on every sign-in. It is why co-founders can never read chats, delete shops or change billing. If a co-founder ever needs more, the right step is an authenticator for them (the founder's own flow, reused), not a longer session.
- Anyone who can run commands on the server can grant access. That is already true of enrolling the founder.

## Not done (said plainly)
Passkeys; a screen for the founder to see grants (the list command and the audit trail show them); notifying a co-founder before their access expires.

## How to revisit
Set no grants and the console is the founder alone, exactly as in ADR 0047. Roles are one table in `modules/auth/roles.py`; the suspicion rules are shared with the founder's (`AdminAuth._suspicion`).
