What sends the founder an alert

Any component records the problem as one open alert per cause (repeats only add a count). The web scheduler sends them: critical at once to email, WhatsApp and the webhook, repeated until resolved; high at once, then only if it happens again; medium in a rollup email; low in a digest email. Critical and high also send a notice when resolved. Part-down and stalled-queue alerts close themselves when the part or queue recovers.

Notes

  • Database: 50 tables, each in exactly one group (checked against the migrations when this page was built). Columns are left out; they would not fit legibly.
  • The event queue is Postgres jobs by default, Redis by setting (QUEUE_BACKEND). A change and its event are written together; any scheduler relays the event onto the queue.
  • Mocks: tools/meta-sim (port 9100, this machine only) plays Meta and the phones; the local model runs inside the agent worker, tools/llm-bridge on port 9200; the in-process simulator runs inside the gateway. "dev: any OTP", "dev: test pay" and "dev: /sim chat" are switches in the web backend. Production refuses to start with the in-product ones on.
  • Not drawn: the worker also queues handoff and deal alerts for its own owner loop; the web frontend can forward Meta's webhook path to receive so one address serves both.
  • Not built: voice-note transcription (deferred, ADR 0015), console passkeys, a card or UPI gateway. Nothing has run against real Meta, a real model or real SMTP.
